## Phase Goal

**As** Daniel who has just approved a listing on the dossier, **I want to** click a "Draft email" button to have the outreach email pre-composed and saved as a Gmail draft (using the AI-generated draft_body from evaluation time), **so that** I only send messages I have consciously chosen to send, without waiting for a slow AI round-trip.

<objective>
Final vertical slice for Phase 2: the opt-in email draft flow. On explicit user action (button click, not automatic on approval per D-13), the system creates a Gmail draft using the pre-computed draft_body from evaluation time (no live AI call per D-15) and queues the draft into agent_state.pending_drafts so the existing /send <id> Telegram command (QUEUE-07 unchanged from Phase 1) can dispatch it.

Purpose: Closes QUEUE-06 (AI drafts email on approval) and QUEUE-07 (explicit /send required to actually send). This preserves Daniel's "always human-in-the-loop for outbound email" invariant while eliminating the friction of composing routine inquiries.

Output:
- New POST /api/draft/{listing_id} endpoint in main.py
- Draft email button in the dossier's approved-listing detail view (index.html), conditional on data availability
- New helper `data_store.get_approved_listing(listing_id)` for the endpoint lookup
- 2 previously-xfail tests now pass: test_draft_endpoint, test_send_command_after_draft
- Final green suite: 11/11 tests in test_pending.py passing
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → FastAPI /api/draft | Untrusted listing_id in URL path crosses here |
| FastAPI → Gmail IMAP | contact_email and draft_body cross into an external mail system as an unsent draft |
| Telegram /send → SMTP → external mail | Approved draft is actually dispatched to a third party (the real estate agent) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-DRAFT-AUTO | Elevation of Privilege (over-authority) | main.py POST /api/draft/{id} + agent_job process_send_commands | high | mitigate | Draft creation is opt-in (button click, not automatic on approval per D-13); actual send requires explicit /send <id> Telegram command from Daniel's chat (QUEUE-07 unchanged). Two-step gate ensures no unintended outreach. |
| T-02-DRAFT-INJ | Tampering | main.py POST /api/draft/{id} | medium | mitigate | listing_id is used only as a dictionary lookup key in properties[] — never interpolated into an email header or body. draft_body / draft_subject / contact_email come from the pre-computed evaluation stored in properties[] (which came from pending[] which came from AI evaluator output — trust boundary already crossed in Phase 1). |
| T-02-DRAFT-XSS | Tampering | index.html Draft email button status message | low | mitigate | textContent only (verified by grep in Task 2 `<verify>`); listing_id inside status string is a controlled numeric kv.ee id anyway. |
| T-02-EMAIL-LEAK | Information Disclosure | index.html + /api/draft endpoint | low | accept | The endpoint response contains `contact_email` implicitly via the "no_email" reason path (a boolean, not the address). No address is leaked to the browser; the address is only used server-side when creating the Gmail draft. |
| T-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages introduced — gmail_client already ships in Phase 1; endpoint is a thin wrapper. |
</threat_model>
