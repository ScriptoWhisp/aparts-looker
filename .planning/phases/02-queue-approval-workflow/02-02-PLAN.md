## Phase Goal

**As** Daniel scrolling through Telegram on my phone, **I want to** approve or reject each pending listing with a single tap on inline buttons directly under the listing photo, **so that** I can triage the queue in under 5 seconds per listing without opening a browser.

<objective>
Second vertical slice for Phase 2: the Telegram approval loop. Ingested listings now surface in Telegram as photo cards with [Approve] [Reject] [More] buttons; tapping Approve moves the listing to the dossier, tapping Reject prompts for a reason and archives it. Purpose: The Telegram flow is the primary UX per Daniel's constraints — a phone-first, single-user workflow that doesn't require opening the web app. Once this ships, the pending queue is actionable from anywhere without the web UI (which lands in Plan 02-03).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram → VPS agent | Incoming callback_query updates arrive via getUpdates polling; untrusted callback_data and untrusted chat_id enter the VPS process |
| VPS agent → app_data.json | State transitions (approve/reject) mutate persistent JSON; concurrent scheduler ticks + web endpoints touch the same file |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-CQ-SPOOF | Spoofing | agent_job.process_pending_action | high | mitigate | chat_id guard: reject callback_query when `cq["message"]["chat"]["id"] != TELEGRAM_CHAT_ID` — implemented in Task 2 as the first check inside process_pending_action, log.warning on drop |
| T-02-CQ-REASON | Tampering | agent_job.process_pending_action + data_store.reject_listing | medium | mitigate | Whitelist reason values {"price","location","condition","other"}; anything else clamped to "other" — enforced in BOTH agent_job dispatcher AND data_store.reject_listing (defense in depth) |
| T-02-CQ-INJ | Tampering | telegram_client.send_pending_card | low | mitigate | callback_data uses static compact format `approve:<id>` / `reject:<id>` / `rr:<reason>:<id>`; listing.id is validated by the ingest schema in Phase 1 (numeric kv.ee object id, 6-8 digits) so no user-controlled data reaches callback_data |
| T-02-DOUBLE-TAP | Repudiation (idempotency) | data_store.approve_listing / reject_listing | low | mitigate | Both functions return False when listing not in pending[]; agent_job displays "✅ Already processed" / "❌ Already processed" to Daniel; no state divergence on race |
| T-02-STALE-MSG | Denial of Service (silent) | telegram_client.edit_card_resolved | low | accept | try/except (requests.RequestException, KeyError) — a stale message_id or deleted Telegram message is logged and ignored; the underlying state change (approve/reject) still committed to JSON |
| T-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages introduced in this plan — all functions use requests + json + dataclasses (already in requirements.txt Phase 1); slopcheck N/A |
</threat_model>
