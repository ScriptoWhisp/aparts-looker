## Claude's Discretion

Areas the user did not want to walk through — the planner decides based on standard practice, using the recommended defaults noted in CONTEXT.md:

- Cutover strategy — recommended: one-shot migration script on first boot; JSON files kept as read-only historical for a week.
- `settings.json` + `agent_state.json` handling — recommended: leave on filesystem, don't migrate; reduces scope.
- Password / connection secrets — recommended: `POSTGRES_PASSWORD` in `.env`; `DATABASE_URL` composed in `config.py`.
- Alembic layout — recommended: `app/alembic/` with baseline autogenerated from models.
- Testing strategy — recommended: hybrid, real Postgres in CI + in-memory SQLite for logic-only unit tests.
- Fate of `data_store._lock` — recommended: audit and remove, replace with SQLAlchemy session scoping (Pitfall 5 rewrite).

## Deferred Ideas

- **Automated backups** — declined; single largest residual operational risk. Recommend as separate follow-up phase (Phase 8 candidate). Cheapest reasonable setup: nightly `pg_dump | gzip | rclone copy` to Backblaze B2 via cron in app container.
- **Multi-source support** — PK-as-VARCHAR leaves room for `source` prefix; not implementing now (no non-kv.ee scraper exists yet).
- **PostGIS** — deferred; Phase 5 uses client-side GeoJSON, no server-side geo queries needed.
- **Query-driven features** (cheapest-per-district, rejected-but-high-score analytics) — separate phases if/when wanted.
- **settings_store migration** — deferred to planner's discretion; likely stays on filesystem.
